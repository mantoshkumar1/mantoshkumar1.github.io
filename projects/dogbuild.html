DogBuild

This page answers: How can multiple AI coding agents coordinate through a durable, auditable control plane without requiring humans to manually relay context?

Currently under active development and not yet a production-ready autonomous-agent platform.

Problem

When coordinating multiple AI agents across different vendors (Claude Code for implementation, ChatGPT for review, etc.), without a control plane, the human becomes the message bus:

  • Implementation complete → human copies result to reviewer
  • Review findings → human carries feedback back to implementer
  • Every round of fixes requires manual relay

That manual relay is structural friction, not a habit to optimize. DogBuild explores how intent, authority, evidence, routing, and handoffs can become deterministic and auditable instead.

Challenge

Can you build a control plane that lets multiple agents coordinate without requiring a human to carry context between them? The technical challenge isn't AI reasoning—both Claude and ChatGPT can think. The challenge is authority, evidence, and routing: who decides what work happens, where does the proof live, and how does one agent hand work to another without losing the thread?

My Contribution

I built DogBuild to test whether a GitHub-first, append-only control model could replace human relay. The core contribution is a lived dogfooding proof of concept demonstrating that the architectural approach is viable with two key design changes: record authority and evidence on GitHub (not in chat), and revalidate exact identity before every write. Full deterministic routing and scheduled autonomous invocation remain under development.

Architecture in use (as of September 2026):

  • GitHub-first evidence: The control model records current routing and authority lineage on control board #180. Detailed append-only evidence—plans, findings, corrections, and proof—remains on canonical issues and PRs. Chat is a wake interface only.
  • Three-server MCP portal: A Cloudflare gateway routes requests through three validated MCP servers (Claude, Cursor, Codex), providing documented tool access without needing unrestricted GitHub permissions. Portal connectivity and tool inventory are end-to-end validated through lived use; tool-surface enforcement and least-privilege boundaries remain in development per #169 and #167.
  • Append-only evidence: Worker plans, findings, and corrections are all timestamped and preserved on GitHub—corrections supersede earlier evidence without silent rewrites.
  • Authority tiers: Founder approves irreversible actions (merge, deploy, spend). Strategy routes work and reconciles evidence. Workers are bounded to assigned tasks.
  • Exact-SHA verification: Current policy and design in PR #184 document that GitHub mutations include exact head SHA and CI evidence linked on the control board for independent review. Universal mechanical enforcement of this policy remains under development per #176.

Engineering Decisions

GitHub as the durable source of truth

Choice: Record all authority, routing decisions, and task state as GitHub issues and PRs, not in chat or private documents. Rationale: GitHub's append-only model and versioning mean decisions can be audited and challenged. Chat disappears; GitHub remains. Trade-off: Slower initial decisions, but decisions become durable and auditable. Mechanical enforcement of policy via the control MCP server remains under development per #176.

Append-only evidence without silent rewrites

Choice: All worker findings, corrections, and supersessions remain visible as separate timestamped comments; never edit or delete historical evidence. Rationale: Prevents defenders of bad decisions from rewriting history. An auditable trail makes blame-shifting impossible. Trade-off: The control board becomes verbose, but transparency is the point.

Exact identity revalidation before every write

Choice: Immediately before any GitHub mutation, the worker re-reads current control state and validates repository, task, role, generation, and requested effect match live GitHub. Rationale: Prevents scope creep from stale chat instructions or missed updates by another worker. Trade-off: Adds latency, but prevents silent authorization drift.

Fail closed on ambiguous authority

Choice: When evidence is missing, conflicting, or stale, stop instead of guessing. Rationale: A blocked worker is better than a worker that silently violated its authority boundary. Trade-off: Requires human intervention to resolve ambiguities, but keeps the system honest about what it doesn't know.

Separate implementation and review

Choice: The session that implements a change cannot be the same session that approves and merges it. Rationale: Self-approval creates conflicts of interest. Independent review catches blind spots. Trade-off: Requires coordination between workers, but prevents a single agent from unilaterally shipping untested code.

Infrastructure-critical verification is adversarial

Choice: For changes to DogBuild itself, happy-path tests are insufficient—require fault-injection, security-negative, high-volume, and boundary-case tests before deployment. Rationale: Control planes must fail gracefully; undiscovered edge cases in routing or authority are catastrophic. Trade-off: Verification takes much longer, but the trust cost is worth it.

What This Project Demonstrates

Durable governance in multi-agent systems

Authority hierarchies that remain explicit and auditable through GitHub-first documentation and append-only evidence trails. The goal is mechanical enforcement across agent boundaries; currently validated through lived process and review practices, with automatic enforcement mechanisms under development.

Append-only evidence as a system property

How to preserve full audit trails and correctness proofs while still allowing corrections, supersessions, and reversals of earlier decisions.

GitHub as a control plane

Using issues, PRs, and exact-SHA proof as the durable source of truth for deterministic multi-agent routing—not as a code repository.

Fail-closed system design

How a control plane can stop and ask for human direction when faced with ambiguous or conflicting evidence, rather than silently guessing.

This project demonstrates my ability to build distributed systems that remain auditable, controllable, and transparent to independent review through real use within the DogBuild project.

Reflection

DogBuild started with a simple observation: when both ChatGPT and Claude exist and can implement and review code, but a human still has to manually carry context between them, the bottleneck isn't reasoning—it's governance. Who decides what work happens next? Where does that decision live? How does one agent hand work to another?

The insight—after months of lived dogfooding—is that the core layers are solvable. Record authority and evidence on GitHub instead of chat. Revalidate exact identity before every write. Make corrections visible, not silent. These documented practices enable a pathway toward agents routing work to each other and approving findings without routine human relay—but this full capability remains the target and is not yet fully proven end-to-end.

DogBuild is not yet production-ready. Safety findings in the listener remain pending. Least-privilege identity is under development. Deployment will require explicit founder authorization with rollback proof. But the core architectural layers—durable, auditable control planes, GitHub-first evidence, and append-only decision trails—are proven through lived use. The path forward requires scheduled worker invocation and independent pre-write verification before full admission. The bottleneck was never the agents. It was always the governance layer.
