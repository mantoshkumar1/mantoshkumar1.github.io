## Why freshness is a separate evidence property

A source can be public, well-cited, and correctly indexed while still describing a past state. A document's `last_updated` field records an editorial update; it is not proof that every fact was rechecked on that date, an expiry time, or a currentness guarantee. A generated answer must not turn old prose into a present-tense claim merely because it remains retrievable.

Ask Mantosh's governing boundary remains the [public-evidence vision](../VISION.md): explain and navigate published engineering work, preserve evidence boundaries, and avoid unsupported inference. This policy therefore treats freshness metadata as a way to decide whether a time-sensitive claim may be phrased as current; it is not a source of new facts.

## What the pinned implementation currently enforces

### Knowledge source and publication path

- [`knowledge/README.md`](../knowledge/README.md) identifies reviewed public Markdown in the category directories as the Ask Mantosh knowledge source. [`knowledge/_template.md`](../knowledge/_template.md) includes `last_updated`, but no freshness class, verifier, review trigger, or expiry field.
- The [knowledge sync workflow](../.github/workflows/sync-knowledge.yml) runs on main pushes affecting `knowledge/**/*.md` and related sync files; its normal path asks `sync-knowledge.mjs` to process changed files, while manual dispatch uses `--all`. The script sends each document's `last_updated` and `fact_*` front matter to the Worker indexer. It validates that `last_updated` is present, not that a fact was verified on that date or is within an age limit.
- The indexer stores document `last_updated` and profile-fact `last_updated` values. The profile query in `MetadataService.profileFacts()` selects only `fact_key` and `fact_value`; the direct profile answer path checks required values but has no freshness check. Search filters for public visibility, not fact age. Consequently the current code can serve a public fact after its source date without qualifying or failing closed for age.
- `scripts/audit-docs.mjs` has a specific résumé-PDF SHA-256 comparison that fails when the PDF changes without a corresponding reviewed knowledge hash. It also checks documented counts, links, and selected stale phrases. It does not scan time-sensitive claims for a review date or enforce a general freshness policy. This is a narrow safeguard, not a freshness contract.

### Page dates and project status

The [Insights publishing guide](PUBLISHING_INSIGHTS.md) describes `seo.config.json` as the source for publication dates, feed ordering, and the three newest homepage items. The [project publishing guide](PUBLISHING_PROJECTS.md) distinguishes editorial project selection from publication chronology and explicitly says `live` is not an uptime probe. These mechanisms order or present content; they do not verify the current truth of the underlying claim.

### Index and cache invalidation

- On an authorized knowledge upsert/delete, `chat-worker/src/indexer.js` updates or removes the document's D1 rows, search text, profile facts, and Vectorize IDs, then calls `bumpKnowledgeVersion()`.
- `chat-worker/src/cache.js` makes that bump conditional: it returns without writing when `env.CACHE_VERSION.put` is absent. Reads fall back to the configured cache version. In the pinned `chat-worker/wrangler.toml`, the KV namespace example is commented out and no `CACHE_VERSION_FALLBACK` variable is declared. That repository snapshot therefore does not demonstrate that the optional version key is bound in production; deployed bindings were not inspected.
- Retrieval and response cache keys include the knowledge version; the response key also includes answer-policy version and audience. Repository defaults are 300 seconds for retrieval, 600 seconds for responses, and 900 seconds for embeddings; environment overrides are possible. If the version key is unavailable, the code falls back to the configured/default version and TTLs, rather than proving immediate invalidation. These are source defaults, not verified deployed retention.
- Pages and knowledge synchronization are separate workflows. A Pages build can publish changed static content while a knowledge sync independently processes changed Markdown. This document does not claim either workflow ran for any commit.

## Proposed policy — not current behavior

The following controls are proposed for review under #53. None exists merely because it is written here.

1. **Label facts by how they age.** When implementation is authorized, add explicit metadata for `durable`, `event-driven`, or `periodic` facts, with a canonical source, last verified date, review trigger, and accountable reviewer. Keep the existing `last_updated` field as an editorial timestamp; do not reinterpret it as verification. Do not add a fixed expiry to personal facts without founder approval.
2. **Use evidence-specific review triggers.** The founder confirms personal and employment facts. A project owner/editor confirms project state and demonstration availability on relevant releases/status changes. Publication dates change only with the actual publication/edit. Source/configuration claims are pinned to a commit; production claims require a receipt or observation with its exact time and scope. Review changeable external assumptions against their current authoritative source before presenting them as current.
3. **Fail safely for stale current claims.** For event-driven facts with no verified state after a relevant change, omit the present-tense answer. Where a dated historical statement is still useful, qualify it with its source/as-of date and link to the canonical public source. Do not substitute model memory or an unverified mirror. For work authorization or other consequential personal facts, do not infer or broaden the published wording.
4. **Make periodic review actionable.** A quarterly editorial review for changeable, non-evented assumptions is proposed as a reminder cadence only; it is not an expiry guarantee and does not make an overdue fact false. If a review is overdue or has no authoritative source, present it as a dated repository statement or omit it as current. Founder/Strategy must accept an owner and cadence before any scheduler or deterministic enforcement is added.
5. **Gate indexing and answer use if approved.** A later bounded implementation could validate required freshness metadata in the existing docs audit/indexing path, preserve it in indexed profile facts, and prevent a missing/overdue event-driven fact from entering a present-tense answer. Add tests and update production documentation only under a separate explicit assignment and existing test authority.
6. **Verify cache invalidation before claiming freshness.** Before relying on immediate changed-fact answers, verify that a version-key binding is actually configured and that index upsert/delete changes the version used by response and retrieval caches. If that cannot be established, describe the observed source/index pipeline and remaining TTL window; do not claim immediate invalidation. A provider/account check or configuration change is outside this documentation task.
