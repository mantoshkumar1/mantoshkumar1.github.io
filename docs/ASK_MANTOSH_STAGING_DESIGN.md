# Ask Mantosh staging isolation — design only

**Status:** Pre-provisioning proposal. This document records repository evidence and a candidate design; it does not provision, configure, authorize, or verify a staging environment.  
**Source reviewed:** `main` at `d8cdb221e47cea9d64eec146ad40a2fbd021c3e1` (27 October 2026).  
**Scope:** Issue [#28](https://github.com/mantoshkumar1/mantoshkumar1.github.io/issues/28), request `WEB-28-STAGING-ISOLATION-DESIGN-R100`. No code, workflow, test, provider, secret, or deployment changes are included.

## Decision summary

Use a separately named Worker and separately provisioned storage and rate-limit resources for any future staging path. The staging path should use only synthetic, explicitly public test knowledge, an independently approved origin, conservative owner-approved request limits, and a smoke runner that targets only the staging Worker. Keep the existing production configuration, production browser origin, and production release path unchanged.

This is a design to take to the owner before implementation. The repository proves what is committed; it does not prove the current Cloudflare dashboard, GitHub environment policy, deployed bindings, secret placement, effective token scope, account budget, or whether any staging resource exists. No such live state was queried.

## Proposed minimal shape

1. **Separate deployment target.** Add a staging-specific Wrangler configuration file, tentatively `chat-worker/wrangler.staging.toml`, rather than adding staging bindings to the current production configuration. This keeps the existing production config shape visible to its release guard. Confirm the chosen Wrangler invocation and config semantics against current official Wrangler documentation before implementation; no CLI command or provider capability is asserted here.
2. **Separate resources.** The owner provisions and records a staging Worker, D1 database, Vectorize index, and rate-limiter namespace. Every staging binding must resolve to its staging resource; a compare of names is insufficient where immutable resource IDs are the effective binding. Do not copy production IDs into a staging file.
3. **Synthetic knowledge path.** Use a small deterministic fixture with a clearly synthetic source and answer. Keep it outside production knowledge publication paths unless separately approved. A staging-only workflow should target only staging and should reject unexpected paths. Because the existing indexer can delete and upsert, test both its URL and bindings before allowing any write.
4. **Minimal workflow.** Add a separate manually invoked staging workflow only after the owner selects its branch/ref policy, OIDC audience and workflow claim, allowed fixture path, credential route, and required permissions. It should pin one source revision, install locked dependencies, run the existing safe tests, validate the staging configuration without deployment, then invoke the staging smoke only after target identity checks. Workflow addition/activation and permission changes require separate authority; this design does not authorize them.
5. **One smoke script.** A future `chat-worker/scripts/staging-smoke.mjs` should accept only an explicitly supplied staging base URL, fail before network access if it matches the production host, and run against the synthetic corpus. It should capture request/response status, revision, and source identity without logging question text, answers, tokens, or private records.
6. **Guard tests.** A future `chat-worker/test/staging-isolation.test.js` plus narrowly scoped assertions in the protected release-workflow contract should prove the staging workflow cannot target the production URL or bindings. Test fixtures should use synthetic values. The precise protected test scope and workflow permissions need separate approval before code changes.

## Controlled synthetic smoke design

Run only after provisioning, binding readback, and a separate owner decision. Do not run this from the current documentation PR.

**Preflight, before network requests**

- Require an exact staging base URL and source revision.
- Compare the parsed host against the production Worker host and reject an exact match; reject missing or malformed host values.
- Load an expected staging resource manifest through an owner-approved, non-secret verification mechanism. Fail closed if any D1, Vectorize, or rate-limiter binding is absent or aliases production.
- Confirm the approved staging Origin is present only in staging and production's exact origin list is unchanged.
- Require an explicit test budget for the AI-backed case. If the account-level budget/coupling is unknown, skip that case and record the smoke as blocked/incomplete rather than claim pass.

**Four cases**

1. **Health:** `GET /health` returns the deterministic service health payload without configuration detail. This is availability evidence only, not proof of data isolation.
2. **Deterministic navigation:** send one fixed portfolio-navigation question to `POST /chat` with the approved staging Origin. Expect the documented navigation action and no retrieved source. Confirm it uses staging guards/storage; this request still exercises the configured public-route rate limiter.
3. **Grounded retrieval:** use one synthetic public fixture, indexed only in staging. Ask a fixed question whose answer is a unique fixture fact. Require a successful response with the exact synthetic source citation. This invokes the retrieval path and may invoke Workers AI embeddings/generation; run only within the separately approved budget.
4. **Failure path:** request an unrelated, high-specificity topic with the same Origin and expect the fixed evidence-boundary response, no source, and no generated follow-up. Separately test missing/unavailable staging rate-limit and D1 guards in offline fixtures, expecting fail-closed errors. Do not disable controls on a live service to manufacture this case.

The smoke result must name the exact staged revision, endpoint identity, fixture revision, cases actually run, outcomes, and skipped/blocked cases. No result from this design exists yet.

## Owner decisions and capability checks before implementation

- Choose the staging hostname/origin and decide whether it belongs in a separate Cloudflare account or an isolated set of resources in the existing account.
- Provision distinct Worker, D1, Vectorize, and rate-limiter resources; read back the effective bindings privately. Resolve whether account-level Workers AI usage is shared and set a nonproduction test budget or defer live retrieval smoke.
- Choose the staging deployment and indexing identities. Review OIDC audience, repository/ref/workflow claims, branch policy, tokenless permissions, and any narrowly scoped staging-only secret placement. No production token reuse.
- Decide the synthetic fixture source and whether it may be committed publicly. Confirm that staging has no production knowledge sync, no real visitor traffic, no private corpus, and no route from the production UI.
- Review exact origin/CORS behavior, endpoint exposure, cache assumptions, request limits, data retention, logs, quota behavior, and the emergency stop procedure.
- Authorize a specific implementation admission covering exact files, workflow permissions, tests, deployment target, evidence required, and stop conditions. The present assignment grants none of those effects.

## Rollback and recovery limits

- **Code/config:** stop staging traffic or deploy the last known staging code only after confirming it is compatible with current staging schema and fixtures. Preserve the exact failed and restored revisions.
- **D1 and Vectorize:** code rollback does not restore database rows, indexes, or migration state. Rebuild/reset only staging resources from the synthetic fixture and reviewed migrations, after verifying the target identity. Do not apply destructive migration reversal or touch production storage.
- **Cache:** TTL expiry is not a data rollback or proof of index consistency. Keep smoke data synthetic and repeat checks with a new fixture/version if cache can obscure the result.
- **Quota and analytics:** requests, model usage, counters, and aggregate events are effects that may persist after code rollback. Set and inspect the staging budget through an owner-approved capability; this design does not assert that account-level provider allocations are isolated.
- **Production:** no production recovery action is authorized by this document. Follow the existing founder-gated production recovery procedure and inspect live state before any action; never infer staging health or production safety from source YAML.
