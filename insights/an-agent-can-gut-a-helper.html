AI-assisted engineering • 3 minute read

An agent can gut a helper. It can't gut a line you're reading.

Keep the assertion in the test. A test whose meaning lives in another file cannot be reviewed by reading it.

Two tests

// I can review this
assert.equal(res.status, 429);

// I have to go somewhere else to review this
assertRateLimited(res);

The second one is tidier. It's also unreviewable at a glance. To know what it checks I have to open another file, and if I'm honest, I don't. I read the name, decide it sounds right, and move on.

That's fine when I wrote the helper last week. It stops being fine when an agent is editing that helper and I'm reading 40 lines of test diff to decide whether a change is safe.

What review actually saw

The old name for this

Prefer repetition over indirection in tests. Sometimes written as DAMP over DRY.

It predates agents by a decade, and the reasoning never depended on them: tests are documentation that runs. Documentation with the important part in a footnote isn't documentation.

DRY is a rule about code you maintain. A test is not that. A test is a claim you check by reading.

Where the line sits

Helpers for setup are fine. Hide all of it:

  • building the request
  • seeding the database
  • spinning up a fixture
  • logging in a user

The line that decides pass or fail stays in the test.

That's the whole rule. Setup can live anywhere. The assertion lives where you'll see it.

Why it matters more now

Protecting a test file does not protect what it imports. A hollowed-out helper neuters every test that calls it, without touching a single owned path.

An assertion sitting in the test can't be hollowed out somewhere else. It has to be edited where you'd see it, in the diff you already read.

So the old advice about readability turns out to also be advice about blast radius. Nice when that happens.

Evidence boundary

A personal preference from my own testing work, not a measured result. The tradeoff is real: this style produces more repetition, and some teams reasonably choose otherwise.
