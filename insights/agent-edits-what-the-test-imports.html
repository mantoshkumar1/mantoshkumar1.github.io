AI-assisted engineering • 4 minute read

Your agent never edits the test. It edits what the test imports.

CODEOWNERS on your test folder covers a file. It does not cover the truth of what the file says.

The gap

Say worker.test.js is protected. CODEOWNERS covers it, CI flags any change, the test count is pinned. Good.

Now the agent edits test-helpers.js. Nobody protected that. It makes assertValidAnswer() return early.

Every test still runs. Still passes. The test file never moved — same name, same body, same count. CODEOWNERS stays quiet, because nothing it owns was touched.

What the list actually covers

Protect a file and you've protected a file. You haven't protected whether what it says is true, because that reaches into everything the file imports.

The list I should have written

The fix isn't a longer list. It's a different question when writing it.

Not which files are tests? but what does this assertion's truth depend on? For me that's:

  • the test files
  • helpers, fixtures, factories, custom matchers
  • CI workflow files
  • the gate scripts, and any baseline number they compare against
  • the config that decides which environment the tests run in

That last line is the one that caught me out. The setting that chose a fake response over a real call mattered as much as any assertion in the file.

CODEOWNERS only works if the agent isn't you

This is the part I got wrong for a while.

CODEOWNERS plus branch protection is the standard answer, and it's a good one. A test-path change requires review from a named owner. Machine-enforced, no scripts to maintain.

Except GitHub won't let you approve your own pull request. Solo, there is no second party, so there's nothing to enforce. The rule is real and it never fires.

It only becomes a gate when the agent commits as someone else — a bot account or a GitHub App. Then you're a genuine reviewer of someone else's change, and the whole native mechanism works.

Until then you're writing your own guard. Mine fails a pull request when a protected path changes without a review label:

CHANGED=$(git diff --name-only "origin/${BASE_REF}...HEAD" -- \
  'chat-worker/test/**' '.github/workflows/**' 'scripts/audit-*.mjs')

[ -z "$CHANGED" ] && exit 0

printf '%s' "$LABELS" | tr ',' '\n' | grep -qx 'approved-test-change' \
  || { echo "::error::Read the diff, then add the label."; exit 1; }

It works. It's also a workaround for not having a second identity, and I'd throw it away the day I set one up.

What it still misses

Any path list can be walked around by moving logic somewhere the list doesn't cover. Draw it carefully and you catch today's routes, not tomorrow's.

Revisit it every time test infrastructure moves. And keep the assertion itself where you can see it — that is the other half of this.

Evidence boundary

The workflow above runs on my own website repository. The bot identity is something I've decided is right and haven't set up. Where a control isn't in place, I've said so.
