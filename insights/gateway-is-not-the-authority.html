The gateway is not the authority

I put one MCP endpoint in front of three GitHub capability planes. It worked — and it exposed the mental model I had wrong.

A gateway can authenticate the caller and route a tool call. It does not, by itself, decide which GitHub identity executes that call, which operations the identity can perform, or whether an agent is authorized to perform them.

The confusion was reasonable

The setup looked simple: one Cloudflare MCP portal, one URL, and three upstream GitHub MCP servers. I expected one policy at the portal to explain the whole security model.

It did not. I was mixing four separate questions:

  • Who can enter? Client authentication at the portal.
  • Where does the call go? Capability routing to the upstream that advertised the selected tool.
  • Who acts on GitHub? The identity represented by the upstream credential.
  • May the agent do this? Tool curation, repository controls, and the workflow's own authority rules.

Those controls cooperate, but none substitutes for the others.

One endpoint, three capability planes

How the portal knows which server to use

The client does not send a vague request such as “use GitHub.” It invokes a specific tool from the catalog exposed by the portal. Each tool retains the identity of the upstream server that published it. The portal routes that invocation back to the same upstream.

That is why the three planes can sit behind one URL without guessing:

  • Core owns issue, pull-request, branch, commit, and repository operations.
  • Projects owns Project v2 item and field operations.
  • Actions read-only owns workflow-run and job inspection without a write path.

The split is not cosmetic. It makes the capability boundary inspectable. A read-only Actions plane cannot quietly become a workflow-dispatch plane just because another upstream can write issues.

Portal policy and upstream authentication solve different problems

The portal's access policy protects the client-facing entrance. It answers whether this person or runtime may establish an MCP session.

The upstream header answers a different question: when Cloudflare calls GitHub, which credential should GitHub evaluate? For GitHub's HTTP MCP endpoints, that header has the standard form Authorization: Bearer <token>. The value belongs in encrypted server configuration, not in prompts, repositories, screenshots, or operational prose.

Repeating the same human-access policy on every upstream is not what gives GitHub access. A separate server policy matters only if that server is also exposed as its own client-facing Access application or if the product explicitly uses it as an additional gate. Upstream authentication is still required because GitHub must authenticate the call leaving the portal.

The canary proved transport, not safety

I tested the boundaries with a disposable issue in the public DogBuild repository. Through the portal, the client created and read the issue, added it to a GitHub Project, moved its status from Ready to Review to Done, inspected a completed Actions run, emitted webhook comments, and finally closed the issue. Every mutation was read back.

The listener received the webhook but initially rejected the control read because it expected experiment markers in the wrong repository context. After the listener path was corrected, it parsed the control schema, generation, revision, strategy identity, and tasks. It then returned NO_ACTION because the event satisfied no unconsumed wake.

That is a useful result: transport worked, parsing worked, and idempotency held. It is not a security certification. The test also revealed that the upstream credential still represented my personal GitHub identity, which is exactly why capability inventory and identity migration remain separate hardening work.

The hardening sequence

  1. Inventory the actual tools. Classify read, bounded write, destructive, administrative, and workflow-triggering operations.
  2. Disable what the workflow does not need. Prefer absence over a prompt instruction saying “do not use this.”
  3. Move to a dedicated least-privilege identity. A working personal token is evidence of connectivity, not a final runtime design.
  4. Re-run exact canaries. Prove required reads and bounded writes still work; prove forbidden operations are unavailable or blocked.
  5. Retire old credentials and local settings last. Cleanup follows replacement proof, never precedes it.
  6. Document recovery privately. Architecture can be public; credential locations, rotation steps, and recovery details belong in restricted operational documentation.

The reusable principle

“It is behind a gateway” is not a security model. A useful design names every boundary: caller authentication, tool routing, execution identity, allowed capability, and irreversible authority.

The architecture became easier to reason about only after I stopped drawing one box labelled “MCP access” and started asking who makes each decision. One endpoint can simplify the client experience. It should not collapse the control model.

Evidence boundary

What this documents: a real DogBuild dogfood setup tested on September 7, 2026, including Core and Projects mutations, Actions reads, webhook delivery, schema parsing, and read-back verification.

What it does not claim: production readiness, formal threat-model coverage, independent security review, or completion of least-privilege migration. Credential values, account identifiers, and private recovery details are intentionally excluded.
