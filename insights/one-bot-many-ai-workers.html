One bot can coordinate many AI workers. It cannot prove who they were.

A practical identity and permission model for routing GitHub work across Claude and Codex without creating a human account for every role.

The account is not the worker

I use different AI workers for strategy, implementation, and review. Which provider fills a role can change: one may be unavailable, another may have the token budget I need, and a third may be better suited to the task.

Creating a GitHub user for every provider-role combination would turn coordination into account administration. A GitHub App ↗ avoids the service-account problem. One private App can receive webhooks, post trace comments, and be installed wherever the coordinator is needed.

But that convenience creates an important boundary: GitHub sees the App's bot identity. It does not see which model, session, or role was behind the App when an action was requested.

The model I would start with

Give the gateway less power than the workers

The gateway exists to observe, route, and record. It does not need the combined authority of everyone it can wake.

  • Gateway App: read content, issues, pull requests, workflow results, checks, and statuses; write issue and pull-request trace comments. No code write, merge, administration, secrets, or deployment.
  • Strategy: read project evidence and write plans, issues, and routing records. No code, merge, secrets, or production action.
  • Implementor: write only to its task branch and pull request. It may add tests, but changing or deleting an existing test requires direct founder approval.
  • Reviewer: read the exact diff and evidence, then write a review anchored to the exact head SHA. No code write or merge.
  • Founder: retains permission expansion, credentials, exceptions, destructive actions, and production authority.

GitHub Apps start without permissions, and GitHub recommends selecting the minimum required permissions. That makes the small gateway envelope a feature, not an inconvenience: compromising the router should not also grant the ability to rewrite the repository it coordinates.

Token-aware routing must not become authority-aware routing

If Claude is unavailable, Codex can fill an implementation or strategy role. If Codex is short on budget, Claude can take the next bounded task. The role contract must remain unchanged across that substitution.

Review is the hard boundary. The broker must not silently turn the producer into its own independent reviewer. A fresh isolated session may be acceptable where the project's governance explicitly allows it. Where a second provider or named reviewer is required, the correct fallback is to queue the review and stop at the gate.

Availability changes staffing. It does not change authority.

Leave a mark before and after

A shared bot still gives useful semantic traceability when every action declares its lineage. A reviewer can start with:

REVIEW_STARTED
role: reviewer
worker: codex
task: pingstep#516
head_sha: b182886c5eab574dce238d8e42838c9552b52815
broker_run_id: route-20260830-0042

And finish with a native review anchored to the same commit:

REVIEW_COMPLETE CLEAN
role: reviewer
worker: codex
head_sha: b182886c5eab574dce238d8e42838c9552b52815
evidence: candidate-quality=success; presentation=success

The exact SHA prevents a clean review from floating forward to changed code. The run id connects the GitHub artifact to the broker's delivery log. The role and worker fields explain intent. None of those fields proves that Codex rather than Claude produced the text; one shared App cannot provide that proof.

When one bot is no longer enough

Separate Apps become useful when the consequence of impersonating a role exceeds the cost of more credentials. GitHub documents that a user or organization can register multiple Apps, and an installation token identifies the App's bot account. Three private Apps could therefore leave three distinct GitHub actors: Strategy, Implementor, and Reviewer.

That is stronger identity evidence, but it is not automatically strong separation. If one broker holds all three private keys and can use them interchangeably, the separation is mostly presentational. Stronger proof requires separate key custody, role-scoped services, and enforcement that prevents one worker from borrowing another role's credential.

My starting point is therefore one low-permission gateway App, strict internal role capabilities, exact-SHA markers, and deterministic repository gates. Split the identities only when the threat model—not the diagram—requires it.

Evidence boundary
