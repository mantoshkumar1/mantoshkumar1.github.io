Release engineering • 4 minute read • Sep 13, 2026

Keep staging moving. Freeze the release candidate.

I made one branch do two jobs: integration and release qualification. It worked, but every new merge invalidated the evidence I had just collected.

The cleaner design is simple: let staging keep moving, and freeze only the exact candidate you are trying to prove.

The bottleneck I created

For a first release, I used permanent staging as both the place where changes integrated and the exact version being qualified for release.

That is safe, but it couples two different jobs. Integration wants movement. Qualification wants immutability.

If a browser run, accessibility check, or system-boundary test takes a long time, I have two choices: stop merging new work, or accept that the next staging commit makes the evidence stale.

With several AI agents working independently, that becomes expensive quickly. The agents are ready to continue, but the branch has to stay still because the release proof is attached to it.

The branch pipeline I want instead

A failed candidate should stay failed

The other useful rule falls out naturally: never patch a release candidate in place.

RC-17 fails
→ keep RC-17 and its evidence intact
→ fix on a normal branch
→ merge the fix into staging
→ cut RC-18
→ qualify RC-18 from scratch where required

That gives each candidate a clean history. It also prevents a dangerous shortcut: changing the test or the candidate until the red result disappears.

My rule for that is the same one I use elsewhere: if the product is wrong, preserve the test and fix the product. If the test itself is genuinely wrong, prove that separately before changing the contract.

Not every commit needs the whole test universe

The frozen-candidate layer also gives test cost a natural place to live.

  • Feature branch: run focused tests for the changed behavior and every mandatory protection tied to it.
  • Staging: run integration smoke plus deterministic change- and dependency-aware tests. If impact is unclear, run more, not less.
  • Release candidate: run the complete release qualification — all required browser journeys, real system boundaries, security, migrations, accessibility, cleanup, and release evidence.

The important constraint is that an agent does not get to decide casually that a test is unnecessary. Test selection before the RC should be rule-driven. The RC is where the full proof converges.

This changes the human role too

Once the pipeline is bounded correctly, I do not need to supervise every implementation, review, staging merge, or repair loop.

The AI agents can have broad execution freedom through staging and candidate creation, while deterministic gates protect the test and review contracts.

The human boundary moves to the place where it is actually valuable:

Show me one immutable candidate that has passed the complete qualification. Then ask me whether to release it.

That is a much cleaner interface than asking for permission at every intermediate step.

The rule

Keep integration moving. Freeze only the thing you are proving.

Staging is a river: it exists to collect work. A release candidate is a snapshot: it exists to be judged.

Making one branch play both roles is safe, but it serializes work that does not need to be serialized. Separating them lets development continue without making release evidence ambiguous.

Evidence boundary

This is a first-person release-engineering lesson from preparing the Free release of PingStep, a product I am building. It describes the branch and qualification model I want to adopt after observing the cost of using one staging branch as both the moving integration surface and the release candidate. It does not claim production-scale throughput, team adoption, or measured delivery-time improvement. The post-release architecture described here is a design decision, not a claim that the complete pipeline is already deployed.
