The AI company control loop

Giving several AI agents a backlog does not create a company. It creates several workers waiting for someone to decide what happens next.

The permanent fix is not a larger prompt or a faster poller. It is a control loop that separates judgment, durable state, dispatch, execution, evidence, and human authority.

The first automation target was the wrong one

My immediate frustration was simple: ChatGPT could set direction, Claude and Codex could do useful work, and GitHub could hold the evidence — but I was still carrying messages between them. If one agent finished early, it waited. If a review created follow-up work, I had to relay it. An hourly scheduler left capable workers idle.

That sounds like a notification problem. It is really an authority problem.

A webhook can wake an agent immediately, but waking it does not answer the important question: what is this agent already allowed to do? Without that answer, event-driven automation merely makes an unsafe or confused system react faster.

The permanent shape

The system needs one strategy manager, one durable control board, an automatic dispatcher, replaceable specialist agents, and GitHub as the evidence surface. Deterministic software moves work through transitions that have already been approved. AI is used where interpretation or imagination is required.

Each layer has one job

  • The founder sets direction and reserves authority. Product direction, material scope changes, production releases, secrets, spending, destructive actions, and other irreversible decisions remain human.
  • ChatGPT manages strategy. It turns direction into an authorized portfolio: priorities, task envelopes, acceptance criteria, dependencies, and the handoffs that may happen without asking again.
  • The central board holds durable intent. It records more than open and closed. Every item has an owner, current state, evidence, allowed next states, and an explicit reason when it is blocked.
  • The dispatcher moves settled work. It watches events, claims ready items atomically, wakes the right adapter, enforces concurrency and retry rules, and records every transition.
  • Claude and Codex perform bounded work. They implement, review, repair, or investigate inside the envelope. They may take the next ready item without waiting for the hourly strategy cycle.
  • GitHub stores code and evidence. Commits, pull requests, checks, reviews, and structured comments are observable facts. They are signals to the control loop, not the complete source of business authority.

Events are signals, not permission

A GitHub App can react immediately when a pull request opens, a review arrives, a check fails, or an agent is mentioned. That removes the hourly delay. It still must not invent the next action.

If the board already says “after implementation, send this to Codex for review,” the dispatcher can wake Codex as soon as the implementation evidence appears. If the review reports an ordinary defect and the task allows repair rounds, it can wake Claude again. Those are known, pre-approved transitions.

If the review exposes a product trade-off, changes the promised scope, requires a secret, or asks for production authority, the dispatcher stops. It routes the evidence to Strategy. Strategy either chooses within its authority or asks the founder one precise question.

This is the key distinction: GitHub activity tells the system that something happened. The control board tells it what that event is allowed to cause.

How agents keep working during the one-hour window

Strategy should not assign one instruction and hope it lasts an hour. It should authorize a small portfolio of independent work with ordering and limits.

An agent finishes one item, publishes evidence, and asks the board for the next claimable item. The dispatcher checks dependencies, ownership, concurrency, and authority before leasing it. If nothing is ready, the agent stops cleanly. If a result unlocks another approved task, the next agent wakes immediately.

Completion is not inferred from persuasive prose. A task reaches a terminal state only when its acceptance evidence exists: the expected commit or artifact, required checks, review disposition, and any task-specific proof. AI can judge whether the evidence satisfies a nuanced requirement; deterministic code can verify that the judgment was recorded by an authorized actor and that the state transition is legal.

Deterministic management does not mean deterministic judgment

Project management cannot be reduced to a finite state machine without losing the most valuable part: noticing a new possibility, revising a plan while learning, reconciling conflicting evidence, and deciding that the original task was wrong.

But the machinery around those decisions can be codified:

  • who may change which state;
  • which evidence is required before a transition;
  • which handoffs are already authorized;
  • how work is claimed, retried, timed out, and recovered after restart;
  • when uncertainty must be escalated rather than disguised as completion.

The AI remains the judgment engine. The surrounding system makes that judgment observable, bounded, and recoverable.

Build it in stages

  1. Prove the protocol with polling. A small local process can watch the control issue and structured agent updates every few seconds. This is enough to learn which states and handoffs are actually needed.
  2. Replace polling with a GitHub App. Signed webhooks provide immediate events. The dispatcher deduplicates deliveries and maps them to authorized transitions.
  3. Make state restart-safe. Leases, idempotency keys, attempt histories, heartbeats, and dead-letter states prevent a reboot or duplicate webhook from losing or repeating work.
  4. Add vendor adapters. Claude, Codex, and future agents receive the same task envelope and return the same result contract even though their runtimes differ.
  5. Keep strategy asynchronous. Event-triggered strategy runs can handle urgent judgment where supported; the hourly run remains a reconciliation and recovery path, not the normal dispatcher.

The real goal is bounded momentum

The useful version of an “AI company” is not a system that never asks a person anything. It is a system that keeps moving through every decision already made, preserves the evidence for every transition, and interrupts the founder only when a genuinely new decision appears.

That gives the agents autonomy without pretending they own the company. It gives the founder leverage without making them the message bus.

This is the architectural follow-up to Why Am I Still the Message Bus Between My AI Agents?. The earlier article identifies the manual relay. This control loop defines the boundary that can safely remove it.

Evidence boundary

What this documents: an architecture derived from an active, multi-agent workflow and the incremental path being used to test it: durable tasks, structured results, bounded handoffs, and event-driven wake-ups.

What it does not claim: that the permanent control plane is complete, production-proven, or generally available. The polling bridge and the event-driven architecture are milestones, not evidence that the final system already exists.
