Deterministic systems should be the immigration officers for AI

Do not ask an AI agent to remember every safety rule. Put deterministic checks at the borders and make unsafe transitions mechanically impossible.

The insight came from a real failure

While dogfooding a multi-agent workflow, two independently reviewed changes were intended to enter staging one after another. The second change had been reviewed against an older staging base. By the time it was merged, staging already contained the first change, so the resulting tree was not the exact tree that had been independently reviewed.

GitHub accepted the squash merge. The deterministic staging gate did not. It stopped before deployment because the final tree no longer matched the reviewed head.

The important lesson was not “make the gate smarter.” The gate was right to refuse the transition.

Think of the gate as an immigration officer

An immigration officer does not ask whether a traveller seems reasonable. The officer checks identity, documents, route, authority, and admissibility against explicit rules. If the proof is missing or inconsistent, entry stops.

AI-controlled engineering needs the same model at every dangerous boundary.

The AI can be creative before the border. The border itself should be boring.

A concrete example: serial staging

Suppose staging is at commit A. PR-1 is reviewed against A, producing reviewed head B. The only acceptable transition is:

A → B

Now PR-2 was also originally prepared against A. If PR-1 lands first, PR-2 must not simply be merged because it is “conflict-free.” Its exact reviewed tree is stale.

The correct sequence is:

A
└─ review PR-1 → B
   └─ deterministic gate accepts B
      └─ rebuild/rebase PR-2 on B → C
         └─ independent review of exact C
            └─ deterministic gate accepts C

This is intentionally slower than allowing a wave of loosely compatible merges. It is also much easier to reason about: every accepted staging state corresponds to one exact reviewed state.

One happy path is a safety feature

AI agents tend to add options, fallbacks, abstractions, and alternate routes. That can look sophisticated while quietly expanding the state space you now have to reason about.

For high-risk actions, I prefer one happy path and explicit refusal everywhere else:

  • Staging entry: one canonical reviewed transition.
  • Production promotion: one human-controlled path.
  • Secrets: only approved stores and identities.
  • Billing/provider actions: exact allowlisted operations.
  • Destructive actions: explicit authority plus deterministic preconditions.

If another path becomes necessary, add it deliberately as a new contract. Do not let an AI infer that two paths are “basically equivalent.”

The test plane matters more than the feature code

With AI-generated code, implementation is becoming cheap. The scarce asset is the protected definition of what must be true.

That changes the job of Strategy. The first responsibility is not to write the feature. It is to define the happy path, encode the tests and deterministic constraints, and protect their meaning from being weakened just because the generated implementation does not fit.

Founder intent
   ↓
Test intent + deterministic constraints
   ↓
AI implementation
   ↓
Independent review
   ↓
Deterministic verification
   ↓
Acceptance

If an implementation cannot pass without changing the test, the default assumption should be that the implementation is wrong. A test changes only when the product intent changed or the test itself is proven incorrect.

Where I would put immigration officers

  • task branch → staging
  • staging → production
  • workflow dispatch and deployment
  • provider and billing mutations
  • secret access
  • repository administration
  • data deletion and irreversible migration steps
  • authority changes and role escalation

The more irreversible the action, the less the final decision should depend on a model remembering prose.

The principle

Do not make AI safe by asking it to behave safely. Put deterministic systems at the borders and make unsafe transitions impossible.

Let the agents reason, draft, implement, review, and explore. But when something is about to cross a meaningful boundary, treat it like a traveller entering a country: exact identity, exact authority, exact documents, exact route. Otherwise, no entry.

Evidence boundary

This article is a first-person engineering lesson derived from my own ongoing AI-assisted development workflow and a staging-governance failure I observed while dogfooding it. It describes the architectural principle and the failure mode without claiming external adoption, universal correctness, or measured business outcomes.
